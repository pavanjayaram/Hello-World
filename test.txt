Build a production-ready Python automation framework to validate SOAP APIs across environments (DEV, UAT, PROD) by comparing responses and integrating results with ALM Octane.

Objective:

The system should:
	1.	Send SOAP requests to DEV and UAT environments.
	2.	Capture XML responses.
	3.	Compare responses at field/column level (not raw XML).
	4.	Identify mismatches clearly.
	5.	Generate a detailed report.
	6.	Push test execution results into ALM Octane via REST API.

⸻

Functional Requirements:

1. Config-Driven Execution
	•	Read input from a JSON config file.
	•	Config structure:
{
“test_cases”: [
{
“test_name”: “getCustomer”,
“operation”: “getCustomer”,
“dev_url”: “DEV_ENDPOINT”,
“uat_url”: “UAT_ENDPOINT”,
“soap_action”: “SOAP_ACTION”,
“request_payload”: “”,
“fields_to_compare”: [“customerId”, “name”, “status”],
“ignore_fields”: [“timestamp”, “requestId”]
}
]
}

⸻

2. SOAP Request Execution
	•	Use Python requests or zeep.
	•	Send request to DEV and UAT.
	•	Handle headers and SOAPAction.
	•	Capture full XML response.

⸻

3. XML Parsing & Normalization
	•	Parse XML using lxml or ElementTree.
	•	Convert XML to dictionary format.
	•	Normalize:
	•	Remove namespaces
	•	Trim spaces
	•	Handle missing tags

⸻

4. Field-Level Comparison
	•	Compare only configured fields.
	•	Ignore dynamic fields.
	•	Output mismatch like:
Field: status → DEV=ACTIVE | UAT=INACTIVE
	•	Also calculate:
	•	Match %
	•	Total fields compared
	•	Total mismatches

⸻

5. Intelligent Comparison Features
	•	Handle:
	•	Missing fields
	•	Null vs empty values
	•	Type mismatch (int vs string)
	•	Support nested XML fields

⸻

6. Report Generation
Generate:
	1.	CSV report
	2.	HTML report (preferred)

HTML should include:
	•	Test Name
	•	Status (Pass/Fail)
	•	Table of mismatches
	•	Match percentage

⸻

7. ALM Octane Integration
Implement:
	1.	Authentication using client_id and client_secret
	2.	Create test run
	3.	Update test result (Passed/Failed)
	4.	Attach report file

APIs:
	•	POST /authentication/sign_in
	•	POST /runs
	•	PUT /runs/{id}
	•	POST /attachments

⸻

8. Logging & Error Handling
	•	Log all steps
	•	Capture API failures
	•	Retry mechanism (optional)

⸻

9. Folder Structure
wsdl_api_validator/
│
├── config/
│   └── config.json
├── src/
│   ├── api_client.py
│   ├── xml_parser.py
│   ├── comparator.py
│   ├── report_generator.py
│   ├── octane_client.py
│
├── reports/
├── logs/
└── main.py

⸻

10. Execution Flow
main.py should:
	1.	Read config
	2.	Loop test cases
	3.	Call DEV & UAT APIs
	4.	Compare responses
	5.	Generate report
	6.	Push results to Octane

⸻

Non-Functional Requirements:
	•	Modular code
	•	Reusable components
	•	Easy to extend for PROD
	•	Config-driven (no hardcoding)

⸻

Output Example:

Test: getCustomer
Status: FAILED

Mismatch:
	•	status → DEV=ACTIVE | UAT=INACTIVE
	•	age → DEV=30 | UAT=NULL

Match %: 85%
